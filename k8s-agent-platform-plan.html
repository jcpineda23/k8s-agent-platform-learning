What you're actually learning

You don't need to be your team's best kubectl operator. You need three things:

  1. An accurate mental model of Kubernetes, so you can tell when a design is fighting the system and when it's working with it.
  2. Fluency in what's different about agent workloads. Most Kubernetes knowledge assumes stateless web services. Agents are long-running, stateful, bursty and expensive, and they run untrusted code. Your edge comes from understanding that gap.
  3. Judgment you can pass on: design-review questions, failure stories and tradeoff calls your team learns from.

    Using Claude Code so you actually learn

    • Write the design doc yourself first. Then ask Claude Code to critique it before any code exists. The design thinking is the part you need to practice.
    • Put a teach mode in each project's CLAUDE.md: "Explain each Kubernetes concept before you implement it. After each change, ask me one question to check my understanding."
    • Make it break things. Ask Claude Code to add a subtle bug (a missing finalizer, a wrong selector, a bad probe) without telling you where, then debug it with kubectl alone.
    • Read every diff line by line. If you can't explain a line, ask for an explanation before you accept it.
    • Turn each project into a team asset. Present it at a brown-bag session; your engineers' questions show you what you still don't understand.
